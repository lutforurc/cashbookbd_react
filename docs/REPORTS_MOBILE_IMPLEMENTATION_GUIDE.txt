CashBookBD Mobile App - Reports Menu Implementation Guide
=========================================================

This guide explains how to implement all reports under the `Reports` menu in
the CashBookBD mobile app. It is based on the current React web app code.

Use this guide together with:
- `docs/ROLE_MANAGEMENT_MOBILE_GUIDE.txt`

The mobile app must show one parent menu named `Reports`. Under that parent
menu, show only the report items the logged-in user is allowed to access.


1. Core Rule
------------

After login, load app settings from:

- `POST /api/settings/get-settings`

Store:

- `settings.permissions`

Use the permission helper functions from the role guide:

- `hasPermission`
- `hasAnyPermission`
- `hasAllPermissions`

If the user has `"*"`, show all reports.

The `Reports` parent menu should be visible if the user has any permission used
by any report child item.

3. Required Mobile Files
------------------------

Recommended mobile structure:

- `mobile-app/src/config/reportMenu.ts`
- `mobile-app/src/services/reportService.ts`
- `mobile-app/src/screens/reports/ReportsHomeScreen.tsx`
- `mobile-app/src/screens/reports/ReportFilterScreen.tsx`
- `mobile-app/src/screens/reports/ReportResultScreen.tsx`
- `mobile-app/src/screens/reports/NoAccessScreen.tsx`

You can also create one screen per report later, but the fastest maintainable
implementation is:

1. A `ReportsHomeScreen` that lists all permitted reports.
2. A generic filter screen driven by report config.
3. A generic result screen that renders rows/cards/totals from API responses.


4. Reports Parent Permission
----------------------------

Use this permission list for the parent `Reports` menu:

```ts
export const REPORTS_PARENT_PERMISSIONS = [
  'date.wise.total',
  'cashbook.view',
  'profit.loss',
  'balancesheet.view',
  'trial.balance.l3',
  'trial.balance.l4',
  'bank.information',
  'connected.member.view',
  'productwise.profit',
  'ledger.customer',
  'installment.create',
  'ledger.due.view',
  'ledger.view',
  'ledger.labour',
  'purchase.ledger',
  'sales.ledger',
  'mitch.match',
  'group.report',
  'product.stock.view',
  'product.in.out',

```

Show the Reports parent menu when:

```ts
hasAnyPermission(permissions, REPORTS_PARENT_PERMISSIONS)
```

7. Dropdown / Lookup Endpoints
------------------------------

Most reports require filters. Add these lookup endpoints as needed:

```ts
export const lookupEndpoints = {
  branches: `${API_BASE_URL}/branch/ddl/all-branch`,
  protectedBranches: `${API_BASE_URL}/branch/ddl/protected-branch`,
  products: `${API_BASE_URL}/product/ddl/list`,
  brands: `${API_BASE_URL}/product/brand/ddl`,
  categories: `${API_BASE_URL}/category/category-ddl`,
  coaL3: `${API_BASE_URL}/chart_of_accounts/ddl/l3-list`,
  coaL4: `${API_BASE_URL}/chart_of_accounts/ddl/l4-list`,
  customers: `${API_BASE_URL}/contact/details`,
  employees: `${API_BASE_URL}/hrms/employee/ddl/list`,
  labourItems: `${API_BASE_URL}/labour/items`,
  areas: `${API_BASE_URL}/area/ddl-list`,
};
```

Default branch:
- Use `user.branch_id` from `/api/me` when available.
- Also load protected branch settings because some report screens use the
  current transaction date from protected branch data.

Date format note:
- Some legacy report APIs use `DD/MM/YYYY`.
- Some newer APIs use `YYYY-MM-DD`.
- Follow the parameter format listed in section 8.


8. Report Request Shapes
------------------------

Use these method, endpoint, and parameter shapes.

Date Wise Total:
- Permission: `date.wise.total`
- Method: `GET`
- Endpoint: `/api/reports/date-wise-total-data`
- Query params:
  - `branch_id`
  - `start_date`
  - `end_date`

Cashbook:
- Permission: `cashbook.view`
- Method: `GET`
- Endpoint: `/api/reports/cashbook`
- Query params:
  - `branch_id`
  - `start_date`
  - `end_date`

Profit Loss:
- Permissions: `cashbook.view` or `profit.loss`
- Method: `POST`
- Endpoint: `/api/reports/profit-loss`
- Body:
  - `branch_id`
  - `start_date`
  - `end_date`

Balance Sheet:
- Permissions: `cashbook.view` or `balancesheet.view`
- Method: `POST`
- Endpoint: `/api/reports/balance-sheet`
- Body:
  - `branchId`
  - `startDate`
  - `endDate`

Trial Balance Level 3:
- Permissions: `cashbook.view` or `trial.balance.l3`
- Method: `GET`
- Endpoint: `/api/reports/trialbalance-level3`
- Query params:
  - `branch_id`
  - `start_date`
  - `end_date`

- Query params:

Bank Information:

- Query params:
  - `branch_id`

Recommended style:

```ts
import { reportEndpoints } from '../config/api';
import { apiRequest } from './http';

const toQueryString = (params: Record<string, unknown>) => {
  const query = new URLSearchParams();

  Object.entries(params).forEach(([key, value]) => {
    if (value === undefined || value === null || value === '') return;
    query.append(key, String(value));
  });

  const text = query.toString();
  return text ? `?${text}` : '';
};

const unwrapReportResponse = (response: any) => {
  if (response?.success === false) {
    throw new Error(response?.message || response?.error?.message || 'Report load failed.');
  }

  return response?.data?.data ?? response?.data ?? response;
};

export const reportService = {
  async getReport(endpoint: string, params: Record<string, unknown>) {
    const response = await apiRequest(`${endpoint}${toQueryString(params)}`);
    return unwrapReportResponse(response);
  },

  async postReport(endpoint: string, body: Record<string, unknown>) {
    const response = await apiRequest(endpoint, {
      method: 'POST',
      body: JSON.stringify(body),
    });
    return unwrapReportResponse(response);
  },
};
```

Then create report-specific wrapper functions only where useful:

```ts
export const fetchCashbook = (params) =>
  reportService.getReport(reportEndpoints.cashbook, params);

export const fetchProfitLoss = (body) =>
  reportService.postReport(reportEndpoints.profitLoss, body);
```

12. Result Rendering Guidance
-----------------------------

API response shapes are not fully uniform. The mobile result renderer should be
defensive:

1. If response is an array, render it as rows.
2. If response has `rows`, render `rows`.
3. If response has `items`, render `items`.
4. If response has `data`, inspect `data`.
5. If response has grouped sections, render collapsible sections.
6. Show summary totals at the top when fields such as `summary`, `totals`,
   `total`, `opening`, or `closing` are present.

Recommended helper:

```ts
export const extractReportRows = (payload: any): any[] => {
  if (Array.isArray(payload)) return payload;
  if (Array.isArray(payload?.rows)) return payload.rows;
  if (Array.isArray(payload?.items)) return payload.items;
  if (Array.isArray(payload?.details)) return payload.details;
  if (Array.isArray(payload?.data)) return payload.data;
  if (Array.isArray(payload?.transactions)) return payload.transactions;
  return [];
};
```

Use currency formatting:

```ts
new Intl.NumberFormat('en-BD', { maximumFractionDigits: 2 }).format(value)
```

Important UI requirement:
- Report results must be shown as table-style rows, not dashboard cards.
- The mobile UI should look like a compact report table adapted for mobile.
- Each data record should be rendered as one rounded row block.
- Inside each row block, show label/value pairs in vertical table rows.
- Labels stay on the left.
- Values stay right-aligned on the right.
- Numeric values must be right-aligned.
- Long text values should wrap but must not overlap the value column.

Because backend field names can vary, normalize each API row before rendering:

const normalizeTrialBalanceLevel4Row = (row: any, index: number) => ({

Use the same pattern for every report:

1. Fetch the report data.
2. Extract rows from the response.

17. Acceptance Criteria
-----------------------

The mobile Reports implementation is complete when:

- The app has one visible parent section named `Reports`.
- All report items appear under that parent section only.
- A report item is visible only when the user has at least one of its required
  permissions.
- The Reports parent is hidden when the user has no report permission.
- Tapping a report opens its filter/result flow.
- Report API requests use the bearer token.
- Backend `403` errors are handled clearly.
- Empty data states are readable.
- Loading states are shown.
- Date and branch filters work.
- At least the current user branch is selected by default.
- Report result data is rendered as compact table-style row blocks.
- Labels are left-aligned and values are right-aligned inside each row block.
- Numeric values are formatted and right-aligned.
- Reports are not rendered as dashboard cards or large summary cards.
- The implementation does not hardcode reports directly in `DashboardScreen`;
  it uses the `REPORT_MENU` registry.
