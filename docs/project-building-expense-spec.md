**তারিখ:** ২০২৬-০৮-০৯
**অবস্থা:** ডিজাইন নোট — কোড শুরু হয়নি, একটি সিদ্ধান্ত বাকি (§৫)
**সংশ্লিষ্ট রিপোজিটরি:** `F:\All_Database\www\cashbook_api` (ব্রাঞ্চ `Lutfor`), `F:\All_Database\cashbookbd_react`

## ১. এখন সিস্টেমে যা আছে

খরচ ঢোকে ভাউচার দিয়ে, তিন ধাপের চেইনে:

```
main_trx_master          ভাউচার হেডার (vr_no, vr_date, branch_id, transaction_type)
      └── acc_transaction_master     (voucher_type_id, financial_year_id)
              └── acc_transaction_details   (coa4_id, debit, credit)  ← টাকা এখানে
```

রিয়েল এস্টেটের কাঠামোও পুরোটাই আছে, কন্ট্রোলার ও রুটসহ:

```
projects → buildings → flats → building_units
                    └── garages
```

চার্ট অব অ্যাকাউন্টসে খরচ মানে **লেভেল-১ এর id = 4 (Expense)**, যার নিচে
Direct / Indirect / Others / Administrative & General — চারটি লেভেল-২ গ্রুপ।

## ২. আসল ফাঁক

`acc_transaction_details`-এ প্রজেক্ট বা বিল্ডিং ধরার **কোনো কলাম নেই**। পুরো
টেবিলটাই আটটি কলাম:

| কলাম | ধরন |
| --- | --- |
| `id` | int unsigned |
| `trx_mstr_id` | int unsigned |
| `pay_branch` | int NULL |
| `coa4_id` | int unsigned |
| `remarks` | text NULL |
| `debit` | decimal(12,2) |
| `credit` | decimal(12,2) |
| `status` | tinyint(1) |

পুরো ডেটাবেস খুঁজে খরচের সাথে প্রজেক্টের যোগসূত্র যা পাওয়া গেল:

| খরচের দরজা | টেবিল | প্রজেক্ট? | বিল্ডিং? |
| --- | --- | --- | --- |
| ক্যাশ/ব্যাংক পেমেন্ট, জার্নাল | `acc_transaction_details` | ✗ | ✗ |
| ক্রয় চালান | `inventory_purchase_masters` | ✗ | ✗ |
| মালামাল ইস্যু | `material_issue_master` | ✓ `project_id` | ফ্রি টেক্সট |
| শ্রমিক বিল | `inventory_labour_masters` | ✗ | ✗ |
| বেতন | `hrm_employees` | ✓ `project_id` | ✗ |
| জমি | `projects.purchase_price` | ✓ (ফিল্ড) | — |

অর্থাৎ প্রজেক্ট-ভিত্তিক খরচ আংশিক ধরা যায়, **বিল্ডিং-ভিত্তিক কোথাও ধরা যায় না**।

## ৩. ডিজাইন — লেজারেই মাত্রা

`acc_transaction_details`-এ দুইটি nullable কলাম ও একটি index:

```sql
ALTER TABLE `acc_transaction_details`
  ADD COLUMN `project_id`  INT UNSIGNED NULL AFTER `coa4_id`,
  ADD COLUMN `building_id` INT UNSIGNED NULL AFTER `project_id`,
  ADD INDEX  `idx_atd_dimension` (`project_id`, `building_id`);
```

### কেন হেডারে নয়, লাইনে

বাস্তবে এক পেমেন্টে একাধিক বিল্ডিংয়ের খরচ থাকে — ৫ লাখ টাকায় ৩ লাখ A বিল্ডিংয়ের
রড, ২ লাখ B-এর সিমেন্ট। হেডারে (`main_trx_master`) রাখলে ক্লার্ককে দুইটা আলাদা
ভাউচার করতে বাধ্য করতে হতো, যেটা বাস্তবে কেউ করে না — একটাই ভাউচার হবে, আর
বিল্ডিংয়ের হিসাব ভুল হবে।

### অর্থ

| `project_id` | `building_id` | মানে |
| --- | --- | --- |
| আছে | আছে | ওই বিল্ডিংয়ের সরাসরি খরচ |
| আছে | NULL | প্রজেক্টের **অভিন্ন খরচ** — জমি, সীমানা প্রাচীর, অনুমোদন ফি, সাইট অফিস |
| NULL | NULL | কোম্পানির সাধারণ খরচ, কোনো প্রজেক্টে যাবে না |

### দুই জায়গায় রাখা যাবে না

মাত্রা লাইনে থাকলে হেডারে **রাখা যাবে না**, "সুবিধার জন্য" হলেও না। দুই জায়গায়
থাকলে একদিন অমিল হবে, আর তখন কোনটা সত্যি তার কোনো উত্তর থাকবে না।

## ৫. বাকি সিদ্ধান্ত — ক্রয়ে খরচ, না ইস্যুতে খরচ

এটাই একমাত্র খোলা প্রশ্ন, এবং এটা হিসাবের সিদ্ধান্ত।

### দুইটি মডেল

**মডেল ক — ইস্যুতে খরচ.** কেনা মানে স্টক বাড়া, খরচ নয়। মাল সাইটে ইস্যু হলে তবেই
প্রজেক্টের খরচ। নিখুঁত, কিন্তু ইস্যু এন্ট্রি নিয়মিত না হলে খরচ কম দেখাবে।

**মডেল খ — ক্রয়েই খরচ.** কিনলেই প্রজেক্টের খরচ; ইস্যু তখন শুধু মালের নড়াচড়া।
সহজ, কিন্তু গুদামে পড়ে থাকা মালও খরচ দেখাবে।

### কোডে যা পাওয়া গেল

**ক্রয় ইতিমধ্যেই খরচে যাচ্ছে** —
`app/Http/Controllers/Inventory/PurchaseController.php:508-515`:

```php
'coa4_id' => 35,                  // "Purchase"
'debit'   => $arras['total'],
```

`coa4_id 35` = "Purchase", যেটি COA লেভেল-১ এর **৪ নম্বর — Expense**। কেনার
মুহূর্তেই টাকা খরচের খাতে যাচ্ছে, স্টক অ্যাসেটে নয়। ডেটাতেও তাই: ওই খাতে ২৫
লাইনে ৩৮,০০,৪৩৬ টাকা ডেবিট।

**মালামাল ইস্যু কোনো হিসাব লেখে না** —
`app/Http/Controllers/Inventory/MaterialIssueController.php:15-24`, ক্লাসের
নিজের ডকব্লক:

> Stock-only (**no GL**), quantity-only (**no rate**), direct issue, over-issue allowed

কোডেও তাই: `material_issue_master` + `material_issue_details` + স্টক আউট।
একটিও লেজার এন্ট্রি নেই, দামও নেই — শুধু পরিমাণ।

### এর মানে

দ্বিগুণ গণনার আশঙ্কা **নেই** — ইস্যু কোনো টাকাই লেখে না। আর মডেল ক-তে যেতে হলে
যা যা বানাতে হবে:

| দরকার | আছে? |
| --- | --- |
| ক্রয় স্টক অ্যাসেটে যাবে, খরচে নয় | ✗ — সব ব্যবসার ধরনে একসাথে বদলাবে |
| ইস্যুতে মালের দাম | ✗ — শুধু পরিমাণ |
| FIFO / গড় মূল্যায়ন ইঞ্জিন | ✗ — কোথাও নেই |
| ইস্যুতে লেজার এন্ট্রি | ✗ |

চারটির একটিও নেই। মডেল ক মানে একটি **ইনভেন্টরি ভ্যালুয়েশন ইঞ্জিন** বানানো —
আলাদা প্রকল্প, এই রিপোর্টের অংশ নয়। উপরন্তু `PurchaseController` সব ব্যবসার
ধরনে ভাগাভাগি করা, তাই এলপি গ্যাস বা রাইস মিলের হিসাবও একসাথে নড়বে।

### সুপারিশ: মডেল খ

1. সিস্টেম ইতিমধ্যেই এটা — বাছাই নয়, স্বীকৃতি।
2. কাজ ছোট: ক্রয়ের যে লাইন `coa4_id 35`-এ ডেবিট হচ্ছে, সেই লাইনে মাত্রা বসালেই
   ক্রয় দরজা শেষ। §৩-এর লাইন-স্তরের ডিজাইনে এটা এমনিতেই ঢুকে যায়।
3. পথ বন্ধ হয় না: পরে মূল্যায়ন ইঞ্জিন বানালে কলাম একই থাকবে, শুধু কোন ভাউচার
   খরচ বহন করে সেটা বদলাবে। রিপোর্ট নতুন করে লিখতে হবে না।

### খ-এর দুর্বলতার সস্তা দাওয়াই

গুদামে পড়ে থাকা মাল খরচ দেখাবে — কিন্তু ইস্যুর ডেটা আছে, শুধু টাকায় নয়,
**পরিমাণে**। ভাগটা কাজে লাগানো যায়:

- **টাকা** ← ক্রয় → প্রজেক্টের খরচ
- **পরিমাণ** ← ইস্যু → কোন সাইটে কত মাল গেল

তারপর একটি মিলকরণ রিপোর্ট: *"প্রজেক্ট A — কেনা ১০০০ বস্তা সিমেন্ট, ইস্যু ৮২০,
বাকি ১৮০"*। ভ্যালুয়েশন ইঞ্জিন ছাড়াই অপচয় ও গুদামে জমা ধরা পড়ে।

## ৬. অভিন্ন খরচ বিল্ডিংয়ে বণ্টন

জমির দাম বা সীমানা প্রাচীর কোনো একক বিল্ডিংয়ের নয় (`building_id` NULL)। রিপোর্টে
এগুলো প্রতিটি বিল্ডিংয়ে যাবে।

**ভিত্তি:** বিল্ডিংয়ের ফ্ল্যাটগুলোর মোট বর্গফুট (`flats`-এ মাপ আছে)। মাপ না
থাকলে সমান ভাগে।

ভিত্তিটা প্রজেক্টে সংরক্ষিত থাকবে, যাতে রিপোর্ট বারবার একই ফল দেয়। এটি শুধু
রিপোর্ট স্তরের হিসাব — স্কিমা বা এন্ট্রিতে হাত পড়ে না, তাই পরে বদলানো যায়।

**রিপোর্টে তিন কলাম রাখতে হবে — সরাসরি / বণ্টিত / মোট।** মিশিয়ে ফেলা যাবে না:
মালিক যেদিন সংখ্যাটা নিয়ে প্রশ্ন করবেন, সেদিন দেখাতে হবে কোনটা সত্যিই খরচ হয়েছে
আর কোনটা হিসাব করে বসানো।

## ৮. ঝুঁকি ও রক্ষাকবচ

### ৮.১ খালি ড্রপডাউনই আসল ঝুঁকি

কলাম nullable। ক্লার্ক প্রজেক্ট না বেছে সেভ করলে খরচটা ট্রায়াল ব্যালেন্সে থাকবে,
কিন্তু কোনো প্রজেক্ট রিপোর্টে আসবে না — কেউ টেরও পাবে না। ছয় মাস পর "খরচ কম
দেখাচ্ছে কেন" প্রশ্ন আসবে।

- রিয়েল এস্টেট ব্রাঞ্চে **খরচের খাতে (COA L1 = 4) প্রজেক্ট বাধ্যতামূলক** — সেভের সময়ই আটকাতে হবে
- বিল্ডিং ঐচ্ছিক, কারণ অভিন্ন খরচ আছে
- **রিপোর্ট ৪ প্রথম দিন থেকেই** — এটি ছাড়া বাকি রিপোর্ট বিশ্বাসযোগ্য নয়

### ৮.২ জমির দাম দুইবার নয়

`projects.purchase_price` একটি ফিল্ড, কিন্তু জমির টাকা ভাউচার দিয়েও বেরিয়েছে।
**লেজারই একমাত্র সত্য** — `purchase_price` ও `buildings.construction_cost`
রিপোর্টের যোগে ঢুকবে না, ওগুলো বাজেট/তথ্য হিসেবে থাকবে।

### ৮.৩ বেতনে বেশি চেষ্টা নয়

একজন প্রকৌশলী তিনটি বিল্ডিংয়ে কাজ করেন; `hrm_employees.project_id`-তে একটিই
প্রজেক্ট। বিল্ডিং-ভিত্তিক বেতন ভাগ করতে হাজিরা-শিট লাগবে, যা নেই। বেতন
**প্রজেক্ট স্তরে** থাকবে, বিল্ডিংয়ে যাবে §৬-এর বণ্টনে। নইলে ভুল নিখুঁততা তৈরি
হবে — সংখ্যা দেখতে নির্ভুল, আসলে অনুমান।

### ৮.৪ পুরোনো ডেটা backfill নয়

বিদ্যমান ভাউচারে প্রজেক্ট NULL থাকবে। অনুমান করে ভরাট করলে ভুল সংখ্যা স্থায়ী হবে।
একটি **কাট-অফ তারিখ** ঘোষণা করতে হবে — "প্রজেক্ট রিপোর্ট অমুক তারিখ থেকে"।

ইস্যুর পুরোনো ফ্রি-টেক্সট `building` মানগুলোও ম্যাপ করা যাবে না — ড্রপডাউনে
যাওয়ার পর ওগুলো NULL থাকবে।

### ৮.৫ ALTER রক্ষণাবেক্ষণের সময়ে

`acc_transaction_details` সবচেয়ে ব্যস্ত টেবিল। দুইটি nullable INT ও একটি index
সস্তা, কিন্তু বড় সার্ভারে ALTER টেবিল লক করে। ব্যস্ত সময়ে চালানো যাবে না।

## ১০. যাচাইয়ের ডেটা নেই

`myappsaasdatabase`-এ রিয়েল এস্টেটের কোনো ডেটা নেই:

| টেবিল | রো |
| --- | --- |

| `buildings` | ০ |
| `flats` | ০ |
| `building_units` | ০ |
| `unit_sales_master` | ০ |
| `material_issue_master` | ০ |

ওই ১০০টি ভাউচার Sales Invoice / Cash Receipt / Cash Payment, আর খরচের খাত মাত্র
চারটি — Purchase, Misc Exp., Salary, Office & House Rent। রিয়েল এস্টেট ব্রাঞ্চও
নেই: `business_type` টেবিলে সর্বোচ্চ id ৮ (৭ = "Construction"), অথচ কোডের কোথাও
`business_type_id = 9` খোঁজা হচ্ছে।

কোড লিখতে এটি আটকাবে না, কিন্তু **সংখ্যা মিলিয়ে যাচাই করা যাবে না**। প্রকৃত
খরচের ডাম্প পাওয়া গেলে §৫-এর ক্রয়-বনাম-ইস্যুর প্রশ্নটি ডেটা দেখেই মীমাংসা করা
যেত।
