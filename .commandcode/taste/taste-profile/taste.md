# Taste Profile

## Coding Style & Correctness
- Data records and summary/metadata (totals, balances) must be structurally separated — e.g. a `{records, summary}` shape — rather than mixed into one array and told apart by matching names/labels: explicitly "do not rely only on matching customer names such as 'Total' or 'Balance'". Summary rows are excluded from row rendering, serial numbering, record counts, pagination and aggregation, and the grand total is computed from the complete filtered dataset regardless of pagination. Confidence: 0.6
- Fix the true root cause of bugs rather than suppressing the symptom. In SQL, do not disable `ONLY_FULL_GROUP_BY`, change global/session SQL mode, or paper over errors with `ANY_VALUE`, `DISTINCT`, or arbitrary aggregates — restructure the query/A)logic instead. Confidence: 0.8
- Prefers preserving existing behavior/semantics while making a fix — keep permissions, company/branch isolation, payload shapes, and other working behavior intact (e.g. when widening a permission grant, explicitly preserve the previously-granted role's rows). Confidence: 0.65
- Scope authorization/permission changes to least privilege: grant only to the specific role(s) intended, never bypass authorization, and never broaden a grant to all roles — a screen that is unreachable is fixed by correcting the mismatched rule, never by removing or loosening its guard, and never by assuming that permission over a similar feature (e.g. Cash/Bank create permissions) authorizes another entry; the intended permission mapping is verified from the real source each entry's guard, menu and search already use. Confidence: 0.75
- Authorization is per-user and is never conferred by configuration: a user may select and open a form only when they already hold the required permission (selecting a choice never grants access), a preference saved by an authorized administrator never lets a user without that permission reach the screen, unauthorized entries are hidden from the menu and search while route guards stay enforced, and a permission-disabled choice is disabled-only — it never clears or overwrites the saved preference. Confidence: 0.65
- Values verifying edge cases (empty/null, duplicates, rounding, repeated inputs) and having parts sum exactly to the whole, instead of producing inflated or duplicated totals. Confidence: 0.55
- Aggregation/counting logic must not produce false positives from row-multiplying joins: when a join can return multiple child rows per parent (e.g. one inventory master with several FIFO detail layers), count distinct parent records (`COUNT(DISTINCT im.id)`) rather than raw joined rows (`COUNT(*)`), so genuinely duplicated records are not confused with legitimate multiple rows. Confidence: 0.6
- A record merely existing is not proof the full operation was applied: reconciliation must compare expected vs actual quantities per product/voucher (accounting for legitimate multiple layers and unit conversions) rather than treating the presence of a row as proof of a complete deduction. Confidence: 0.6
- Comparisons must be period- and timing-aware: never compare figures from different time bases (e.g. a historical opening-stock balance against current live stock) without accounting for the reporting period and the movements that occurred in between. Confidence: 0.55
- A global database-level constraint (e.g. a UNIQUE index on a shared table such as `inventory_masters.main_trx_id`) must not be recommended until its compatibility is proven: audit every module that writes the table and determine whether multiple rows per key are ever legitimate ("do not recommend a global UNIQUE constraint unless its compatibility is proven"), and where that negative cannot be established, prefer a narrowly-scoped layered guard — a `SELECT ... FOR UPDATE` lock plus a constraint on the document-specific table plus an expected-vs-posted quantity check — over a global constraint. Confidence: 0.6
- For a bulk operation over many records, prefer per-record atomic transactions with an explicit per-record success/failure report over a single all-or-nothing batch transaction: one failed record must not roll back the rest or leave an inconsistent state, and every failure must be surfaced rather than silently skipped. Confidence: 0.6
- For an import/bulk-upload flow this inverts to all-or-nothing: validate the full batch first, then write in one transaction, and refuse the ENTIRE import on any blocking error so no partial customer/balance records are written — and the backend re-validates at final submission rather than trusting the preview/frontend check. Confidence: 0.6
- An unassigned/missing association (e.g. a stock movement with no warehouse/godown) must be shown as its own explicit bucket/category in a report rather than being dropped or silently attributed to an unrelated real entity, and the surrounding (e.g. branch-level) totals must be preserved. Confidence: 0.55
- In financial notes/explanations, keep distinct measures distinct and never imply they always agree: a recorded figure (e.g. a write-off's captured cost) and its derived valuation/effect (e.g. its effect on inventory valuation and the cost of goods sold) may legitimately differ (multiple purchase prices), so they must not be presented as interchangeable. Confidence: 0.55
- An optional/supplementary fetch added to a report must degrade gracefully and race-safely: a failure never fails or clears the report, and an unread/failed value is never taken as a confirmed zero (absence means the note/section is simply omitted). The in-flight request is abandoned when the scope changes so an older response can never land on newer filters, and printing is held back while the read for the displayed scope is still pending so a printed report can never silently lose the section. Confidence: 0.65
- A figure derived for a report must be fetched over exactly the branch and period that report's own result was computed from — the applied filters the server reports back, not the visible date-picker values (the visible start date does not necessarily represent the reporting period). Confidence: 0.6
- Extends existing functionality on the current database structure rather than introducing new tables/columns: when the existing schema (e.g. an existing master-detail structure) already supports the requirement, add no new tables — instructs explicitly to "not create unnecessary new tables if the existing database structure already supports multiple detail rows". Confidence: 0.65
- A single document/voucher that saves several detail lines must be persisted atomically: all the detail rows and their shared master are written inside one database transaction, so one bad/invalid row rolls the whole voucher back rather than leaving a half-written document (the requested `DB::transaction()` / all-or-nothing guarantee), while existing foreign keys, voucher numbers, approval workflow and audit fields are preserved. Confidence: 0.6
- Prefers extending an existing API to carry the new fields rather than creating a new endpoint: first check whether an existing API already supports the operation, and if so extend that endpoint ("extend the existing API ... instead of creating a new API unnecessarily"), reserving a brand-new endpoint for when no existing one genuinely fits. Confidence: 0.6
- A scoped edit must not reformat code it did not change: never run a code formatter's write mode (e.g. "do not run prettier --write on existing files") over existing files, so the diff carries only the intended change and no whole-file formatting churn. Confidence: 0.6
- When one business type/configuration needs a materially different screen, prefers a dedicated, purpose-built component routed by the existing detection — explicitly "not a modification of" the general component — over adding conditional branches into the shared screen, while still reusing the shared components, helpers and backend services so accounting logic is never duplicated ("a new form does not mean duplicating accounting logic"). Confidence: 0.55
- Keeps user-facing display labels decoupled from internal naming: an option's inner value/component name stays exactly as it is while the user sees its own friendly, neutral label — a copy/label change must never cascade into renaming components or internal identifiers ("Display the friendly names … instead. Keep existing component names and internal identifiers unchanged."). Confidence: 0.5
- When two ways of working are made mutually exclusive (e.g. a branch's unified Received/Payment Entry vs its separate cash/bank forms), each choice is independent and the inactive way is never destroyed: choosing one mode disables — rather than clears or removes — the other mode's selectors, keeps their saved values and re-saves them untouched, shows a short explanation of why they are disabled, ignores those saved values at runtime while the mode is active, and restores the selectors and their previous selections when the user switches back. Confidence: 0.55

- Never disable foreign-key checks or redesign the schema to make a destructive/bulk operation work: the operation must be ordered through the existing constraints and mechanisms, and the existing schema relationships are preserved (no new foreign keys) rather than altered. A table that is genuinely absent is skipped, but an unknown table, an unresolved ownership path, or any leftover dependency must block execution with a clear error instead of silently leaving company data behind. Confidence: 0.7
- A lock or guard acquired to serialize a write must be held for the whole enclosing transaction — released by commit or rollback, reliably on both success and failure — not merely during the helper call that acquires it. Confidence: 0.7

## Workflow
- The user explicitly controls git operations: never commit, push, or deploy unless asked to. Confidence: 0.8
- Database work must stay non-destructive: never run destructive database operations and never modify production data (instructs this explicitly in task specs). Read-only inspection of the schema/rows (e.g. `SHOW COLUMNS`, `db:table`, a `SELECT`/`CAST` probe) is expected and welcome. A defect is likewise never "fixed" by editing data — changing the record itself, its account classification or its approval status to force a record into (or out of) a report is explicitly ruled out. This also bars creating test records/vouchers in the live system to exercise or verify a feature. Confidence: 0.75
- Takes the commit/push split literally: a bare "commit" instruction means commit only — push (and deploy) is never inferred from it, only from an explicit "push". Confidence: 0.6
- Expects git conflict resolution to be a careful semantic merge, not a mechanical pick: read both sides and preserve the intended functionality and recent changes from each, and explicitly "do not blindly choose ours or theirs". Confidence: 0.55
- Expects git work to stay non-destructive and bounded: preserve unrelated uncommitted work, do not start a new merge/rebase/pull, and never use destructive reset/clean commands. Confidence: 0.55
- For conflict work, wants the resolved files staged (when required) but nothing committed, pushed, or deployed, followed by a summary of the resolved files, the decisions taken, verification results, and any remaining in-progress git operation (or a clear statement that no conflicts exist). Confidence: 0.55
- Wants investigation/reporting before implementation: explicitly gates changes ("do not make any changes yet") and expects an upfront statement of capabilities and limitations (including whether results can actually be verified) before work begins; for a scoped change this pre-implementation report must give (1) findings on the data actually available and the verified current behavior, (2) the exact proposed user-facing wording/copy, and (3) the exact files and minimal changes required. Confidence: 0.7
- A build/test is judged by the command's real exit code, not by how its output looks: never pipe the build through something that masks the status ("check the real exit code, do not pipe it"), and report the actual exit status as the pass/fail evidence. Confidence: 0.6
- Runs explicit read-only audit passes where the deliverable is findings only — no code, style, functionality, or config changes (and no commit/push/deploy). Confidence: 0.75
- Verification/audit runs must leave the environment pristine: use only the automated checks already available in the repo (build, editor diagnostics, greps) and never install dependencies or modify project configuration to enable a check — when the repo has no installed type-checker, say so and substitute a manual/other check rather than installing one. Confidence: 0.6
- Will not use credentials found in source files or audit documents; requires an explicitly approved, disposable/non-production test account with a broad read-only role to reach authenticated areas. Confidence: 0.8
- For audits/large sweeps, demands exhaustive coverage of every discovered route/page, worked through in manageable batches, rather than a few representative samples. Confidence: 0.7
- Once the approach/authentication is confirmed, prefers the agent to proceed autonomously through the remaining batches without pausing for further confirmation on non-destructive, read-only work. Confidence: 0.7
- Maintains a route-by-route coverage ledger and expects tracking artifacts kept current; stale/paused status notes (e.g., a TODO still marked "waiting on login") should be updated as soon as their blocker is resolved. Confidence: 0.65
- Verifies UI/visual work against the running application (dev server) using real browser screenshots where possible, rather than reasoning purely from source. Confidence: 0.55
- When asked to verify the actual UI, expects the real rendered output to be exercised (e.g. rendering the actual component and asserting its markup) — a passing build/typecheck alone is not accepted as UI verification, and when the live app can't be driven (needs backend/login) that limitation must be stated along with what was actually rendered. Confidence: 0.55
- Never prints/echoes secret values (passwords, tokens) in output; restricts auth automation to an explicitly approved disposable test account. Confidence: 0.75
- Expects anything produced for sharing from their app (demo videos, walkthroughs, screenshots, marketing material) to contain no credentials or personal information: password fields stay masked, password columns in demo-account tables stay hidden/commented out, and user phone/email must not appear on screen — and this must be verified against the real rendered output rather than assumed. Confidence: 0.6
- Demo/tutorial output must carry the correct branch/tenant branding (the brand the tenant actually uses), not a stale or mismatched one — when the app's own header/sidebar brand diverges from the working branch, wants the correct branch branding used and the mismatch flagged. Confidence: 0.55
- For instructional/tutorial videos of the app, wants each step overlaid with a clear caption in Bengali — a step number/title plus an optional smaller subtitle — whose style and placement match the provided reference file, synchronized with the real on-screen actions (the actual clicks, typing, selections and results), and paused long enough for viewers to read before moving on. Confidence: 0.65
- Walkthrough/demo videos are exported to a concrete, stated spec: 1920×1080, 30 fps, MP4 with H.264 video and AAC audio. Confidence: 0.7
- For a multi-part deliverable (e.g. one tutorial per feature), wants exactly one sample produced first and its file path provided for review, then waits for explicit feedback before generating the remaining items or uploading anything. Confidence: 0.7
- For app tutorials, wants the real UI driven end-to-end — actual clicks, typing, dropdown selections and a genuinely saved document — explicitly not simulated actions or static screenshots standing in for the workflow. Confidence: 0.65
- Tutorial/demo figures must be the real ones: never fake a displayed amount or alter existing balances/history to match a provided example — if the specified figures don't match the live data (prices, balances), show and explain the actual values instead. Confidence: 0.65
- A tutorial must not create duplicate documents: exactly one real record is saved for the demo, and a stray document left by a retake or a failed attempt is deleted and the affected customer balance/stock restored so the demo state matches the one the video shows. Confidence: 0.6
- Voiceover: if a Bengali voiceover exists it is synchronized to the same step instructions; if not, the complete tutorial is delivered with Bengali titles and captions and the missing voiceover is stated explicitly. Confidence: 0.6
- Does not want a tutorial compressed into a fixed short length (e.g. 90 seconds); clarity wins, with pauses long enough to read the titles, prices, totals and invoice number. Confidence: 0.55
- Expects the finished video itself watched/visually verified before delivery — the whole run-through, including Bengali glyph rendering and the saved document's real result — not just the pre-record checks. Confidence: 0.6
- Works on Windows and expects commands/instructions that run in Windows PowerShell — does not assume Unix conventions (e.g., Ctrl+D for stdin) apply. Confidence: 0.75
- The command shell actually executes in Windows cmd.exe (not bash or PowerShell): commands are chained with `&&` (a `;` is not a separator there), there are no heredocs, and files are removed with `del`. Confidence: 0.7
- The two repos live side by side under `F:\All_Database\`: the React frontend at `F:\All_Database\cashbookbd_react` and the backend API at `F:\All_Database\www\cashbook_api` — paths such as `D:\www\cashbook_api` carried in older audit/doc files are stale, and the user states the correct location to correct the agent's assumption. Confidence: 0.6
- Verifies tooling/CLI syntax against actual `--help` output rather than assuming flags exist. Confidence: 0.6
- Wants to see/interact with the exact browser window being automated (foregrounded window or a streamed/dashboard view) rather than acting on a window they cannot observe. Confidence: 0.6
- When fixing/resetting tooling, scope destructive actions tightly to the isolated task process — restart only the audit/agent session and never close, kill, or disturb the user's own personal browser or other unrelated processes. Confidence: 0.6
- Expects prior work artifacts (audit findings, screenshots) to survive environment restarts/resets rather than being lost. Confidence: 0.5
- For a rename/refactor, expects every related reference updated across both the API and React repos — response keys and data mapping, types/variables/calculation references/renderers, print/PDF/export, sample data, tests and configuration — followed by a sweep confirming no obsolete references remain (except explicitly required compatibility handling). Confidence: 0.6
- Verifies a rename with distinct sample amounts per category so a silent swap cannot pass, confirming each category shows its correct label with its original data, screen/print/export agree, and grand totals are unchanged. Confidence: 0.6
- Before executing any diagnostic or repair command (e.g. an artisan dry-run/repair command), wants its implementation read — including the services it calls — to confirm it is genuinely non-mutating, and that confirmed safety reported before running it; if the side effects are at all uncertain, does not want it executed, but the concern reported together with a read-only alternative (e.g. an equivalent set of SELECT queries). Confidence: 0.65
- Historical/legacy record corrections require separate, explicit approval: never auto-repair (no automatic re-approve, unpost, resync, or quantity/stock edits) — instead deliver a reconciliation report that classifies the affected records and recommends the safest action per category for the owner to rule on. Confidence: 0.6
- A change that would touch a shared service used by multiple modules/features is designed as its own separate stage: first verify the impact on every other caller (and on historical valuation/data) and get it approved before modifying the shared code. Confidence: 0.55
- Respects an explicitly stated scope boundary literally: when the needed data/change is not available within the permitted area, stop and explain the dependency (offering an in-scope alternative) rather than expanding scope to other reports, shared helpers/components, APIs, accounting calculations, the database, or existing transactions — and commits to changing only the named area. Confidence: 0.6
- Treats existing, reportedly working features as given when the request is a straightforward preference/configuration: explicitly wants no investigation into whether those existing features work or are compatible, and no proposal to redesign their stock, accounting, or business logic — report only the minimum changes needed and do not expand the task into a broader redesign. Confidence: 0.6

- Destructive verification is wanted but must be fenced to a disposable environment: destructive tests run only against an isolated test database and test file storage, and nothing is created, edited or deleted in live/demo branches — the required proof comes from exercising the real code against that throwaway copy, not from skipping the destructive steps. Confidence: 0.6
- Never trust a client-supplied tenant identifier: ownership (e.g. the company/branch to act on) is resolved server-side from the authenticated user's own session, and the corresponding authorization is enforced on the backend regardless of whether the frontend showed the option. Confidence: 0.55

## Communication & Reporting
- Does not invent policy, legal, or compliance facts — support addresses, completion deadlines, retention periods, legal requirements, or backup guarantees — and does not claim a live URL or deployment without verification: such facts come from verified existing configuration/policy, missing policy decisions and remaining blockers are reported explicitly, and a destructive change is never described as completed unless it actually finished. Confidence: 0.75
- When a fact depends on external/authoritative state (e.g. which versionCodes have already been uploaded to a store), does not want it inferred from local files alone: verify against the authoritative source, and if it cannot be checked, report that verification as outstanding rather than assuming the next value. Confidence: 0.7
- Prefers written deliverables (report findings, plans/specs, summaries) in English; when a document is drafted in another language (e.g. Bengali), wants an English version. Confidence: 0.75
- For a navigation/UX review, wants the deliverable structured as: the problems identified and their user impact; recommended improvements with the reasoning behind each; a current-vs-proposed comparison; a simple visual mockup/wireframe of the proposal; and an explicit prioritization of what should be done now vs what can wait. Confidence: 0.6
- Wants findings delivered as a structured table with explicit columns: page/module + route, the specific inconsistency, evidence (screenshot or source file), user impact, severity (High/Medium/Low), recommended correction, and whether the fix belongs in a shared component/theme or an individual page. Confidence: 0.8
- In a review/audit, expects findings grouped into distinct classes — confirmed bugs vs UI/usability improvements vs optional feature suggestions — and each finding tagged with the layer it needs (frontend, API, or database); explicitly wants missing features distinguished from features that already work. Confidence: 0.6
- Prioritizes improvements that are practical for daily operators over speculative or cosmetic work when ranking review findings. Confidence: 0.55
- Wants intentional design differences distinguished from genuine inconsistencies, and repeated issues grouped into a single finding that lists affected pages. Stylistic observations (e.g., a grey default CTA) are framed as recommendations unless they clearly breach an established design rule. Confidence: 0.7
- Prefers fixes to live in the shared design system — theme tokens and shared components as a single source of truth — over per-page one-off patches; flags hardcoded styles and duplicated patterns. Confidence: 0.6
- Requires claims to be backed by conclusive evidence: distinguishes observed behavior from a diagnosed root cause and rejects indirect signals (e.g., empty login fields or empty browser storage) as proof of a conclusion. Confidence: 0.75
- Scopes verification claims strictly to what was actually checked: never describes a page as "clean"/passing beyond the states and checks performed, and explicitly distinguishes sampled (representative breakpoint or dark-mode) checks from fully verified routes. Confidence: 0.8
- Wants one consolidated final report (severity, evidence, recommended fixes) that also enumerates remaining coverage gaps. Confidence: 0.7
- For a "why did my specific record behave wrong" investigation, expects the actual data verified for that record rather than a code-level explanation alone: the conclusion must be backed by the real records (or a concrete, runnable read-only query that would produce it) and must clearly separate confirmed data-level findings from code-level risks; when the affected record cannot be identified or the check could not be run, wants that limitation stated explicitly instead of guessing counts, quantities or values. Confidence: 0.65
- Wants each verification item reported as PASS / FAIL / NOT TESTED accurately; syntax, lint, build, or formula checks alone do not count as end-to-end verification, and untested areas must be called out rather than implied as passing. Confidence: 0.7
- For a rename, wants the final report to state the exact old→new key/label mappings, the modified files, the verification results, and the deployment compatibility requirements (whether a data patch/migration is needed and whether mixed old/new versions interoperate). Confidence: 0.6
- Findings that depend on third-party hardware/software must be grounded in the vendor's own current official documentation with the sources cited, and distinct models/firmware variants are never assumed to behave identically; anything unverified is labelled as such, together with the exact information (documents, screenshots, captures) still needed to settle it. Confidence: 0.6
- On a follow-up turn after a plan/spec has already been written and saved, does not want it rewritten or re-summarized ("do not rewrite the same plan again", "do not repeat the plan summary"): expects a short delta report answering only the specific open questions — findings that change the plan, whether the existing code supports the required behavior, whether the related flows are correctly handled, and any remaining blockers or decisions. Confidence: 0.6
- An implementation plan is expected to spell out every proposed change in a fixed four-part form — what is created/modified, the relevant file/table/component, why it is needed, and whether it is mandatory or optional — with reuse of existing functionality kept clearly distinct from genuinely new work, and to close with the list of decisions/clarifications required before implementation. Confidence: 0.55
